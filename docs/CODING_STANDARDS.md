# Coding Standards

> Part of the JARVIS OS Architecture Bible. See `JARVIS_ARCHITECT.md` for the
> system-wide index. `EVOLUTION_ENGINE.md`'s per-file code (not its
> orchestration — see that doc's Orchestration section) is the reference
> standard these rules are drawn from.

These rules are **mandatory** for all future JARVIS OS code, whether written
by a human or generated by the Evolution Engine / an AI assistant. Code that
violates these rules should not be merged; if a task cannot be completed
without violating one, stop and say so (see `JARVIS_ARCHITECT.md` §7).

## Language & Runtime

- **Target Python 3.14.** Use modern syntax already present in the best parts
  of the codebase (`from __future__ import annotations`, `X | None` unions,
  `dataclass(slots=True)`, structural typing via `collections.abc`).
- Use **`pathlib.Path`** exclusively for filesystem paths. Never use
  `os.path.join`, raw string concatenation for paths, or hardcoded path
  separators. (`app/core/config.py` already does this correctly — follow it.)
- Every public function, method, and dataclass field must carry a **type
  hint**. No bare `def run(self, request):` — annotate the parameter and
  return type even when the type is `Any` or a forward reference.

## Production-Readiness Rules

Future code **must not** contain:

- Placeholder implementations (`raise NotImplementedError`, `pass`, or a
  docstring standing in for a body) merged as if the feature were complete.
  The five AI providers under `app/ai/providers/` are the canonical example
  of what NOT to leave behind — each one has a public API and a name-shaped
  hole where its body should be.
- `TODO`/`FIXME`/`XXX` comments as a substitute for doing the work. If a task
  is genuinely out of scope, it belongs in `ROADMAP.md`, not a code comment.
- Fake or mocked behavior presented as real (e.g. a provider that returns a
  canned string instead of calling its API).
- Unnecessary comments — comments that restate what the code already says
  (`# Register Core Services FIRST` above a block literally named that) are
  disallowed. `app/core/kernel.py` is the current worst offender for this and
  should be cleaned up before it's used as a reference. Comments should only
  explain **why**, not **what**.
- Per-file "Version: X.Y.Z" header comments (see the stub files under
  `app/memory/`). Version is tracked once, in `Config.VERSION`.

## Structure

- **Follow SOLID.** Concretely, for this codebase:
  - *Single Responsibility*: keep one class per concern per file, as the
    `evolution/` package already does (`GitManager` only runs git,
    `SecurityValidator` only validates, `ProcessRunner` only runs processes).
  - *Open/Closed*: new skills, providers, and brains are added by creating a
    new class that implements an existing abstract contract (`Skill`,
    a future `AIProvider` Protocol) — never by adding `if provider_name ==
    "new_thing"` branches to a router.
  - *Liskov Substitution*: every `Skill` subclass must be usable anywhere a
    `Skill` is expected. This is currently violated by
    `app/skills/generated/calculator.py`, which is not a `Skill` at all (see
    `PLUGIN_SYSTEM.md`) — do not replicate this pattern.
  - *Interface Segregation*: prefer small `Protocol`/`ABC` contracts (see
    `DESIGN_PRINCIPLES.md` for the proposed `AIProvider` protocol) over large
    manager classes with unrelated methods.
  - *Dependency Inversion*: depend on the `ServiceRegistry` and injected
    abstractions, not on concrete singletons. `app/core/event_bus.py`
    exporting both an `EventBus` class and a module-level `event_bus`
    singleton is an anti-pattern to retire, not extend — always go through
    the registry.
- **Follow Clean Architecture layering**: domain/model types
  (`SkillResult`, `MemoryRecord`, `CortexRequest`) must not import from
  infrastructure (`subprocess`, `customtkinter`, provider SDKs). Skills and
  handlers are the boundary layer; core/domain logic underneath them stays
  framework-agnostic.
- **Be modular.** A module should be usable and testable without booting the
  whole kernel — `app/cortex/normalizer.py` and `intent_detector.py` already
  achieve this (pure functions/classes, no I/O). Use them as the template for
  new logic, not `app/gui/window.py`-style code that mixes UI construction
  with business logic.
- **Be testable.** Constructor-inject dependencies (as `Skill.setup(registry)`
  does) rather than reaching for globals inside a method body.

## Logging

- Use `app.core.logger.JarvisLogger` everywhere. Do not call
  `logging.getLogger(__name__)` directly in new code — `app/evolution/`
  currently does this and it should be reconciled, not copied further. See
  `LOGGING_GUIDE.md`.

## Avoiding Duplication & Circular Imports

- Before adding a new router, intent detector, or dispatcher, check whether
  `app/core/router.py` or `app/cortex/` already owns that responsibility —
  the project currently has two overlapping routing implementations; do not
  add a third.
- Skills, providers, and brains import from `app.core` and `app.skills.base`/
  `app.skills.result`, never the reverse. `app.core` must never import from
  `app.skills`, `app.gui`, `app.voice`, or `app.evolution`.

## Backward Compatibility

- Public method signatures on `Skill`, `SkillResult`, `MemoryManager`,
  `ServiceRegistry`, and `EventBus` are part of the plugin contract. Changing
  them requires updating every implementer in the same change and noting the
  break in `ROADMAP.md`.
- The Evolution Engine's own reviewer/generator prompts already encode this
  rule ("Preserve class names and public methods") — apply it to
  human-authored changes too.

## Formatting

- 4-space indentation, no tabs.
- Line-ending consistency: the repository currently mixes CRLF (`\r\n`,
  most files) and LF (`app/evolution/*.py`). Standardize on LF for all new
  and edited files and normalize via `.gitattributes` (`* text=auto eol=lf`)
  as a roadmap item.
- One blank line between methods, two between top-level classes — follow the
  existing convention in `app/core/registry.py`.
